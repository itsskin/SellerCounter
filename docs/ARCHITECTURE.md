# Архитектура SellerCounter

## Идея

Автономное устройство на ESP32-S3, которое само (без внешнего сервера) опрашивает
API маркетплейсов (Ozon, Wildberries, Yandex Market, ...) и показывает на
e-paper экране количество продаж и выручку за день. Настройка — через
веб-страницу, которую поднимает сама плата.

Backend отдельного сервера нет: вся логика (HTTP-клиенты к маркетплейсам,
конфигурация, веб-интерфейс настройки, рендер экрана, зуммер) живёт в
прошивке ESP32 (MicroPython).

## Жизненный цикл устройства

1. **Первое включение / нет сохранённого Wi-Fi**
   - ESP32 поднимает точку доступа (`network.AP_IF`), SSID/пароль заданы в
     `config.py` (`DEFAULT_CONFIG["ap"]`).
   - Поднимается веб-сервер (`web_server.py`) на `192.168.4.1`.
   - Пользователь подключается к точке доступа телефоном/ноутбуком, заходит на
     `http://192.168.4.1/`, вводит SSID/пароль домашнего Wi-Fi.
   - Плата сохраняет конфиг (`/config.json`) и перезагружается в режиме STA.

2. **Обычная работа (STA)**
   - Подключение к Wi-Fi по сохранённым данным.
   - Веб-сервер продолжает работать и в STA-режиме (для донастройки API-ключей,
     маркетплейсов, дизайна) — доступен по IP, который устройство получило по
     DHCP. Этот IP мелко выводится в углу экрана.
   - Асинхронно (`uasyncio`) крутится `stats_engine.py`:
     - раз в `poll_interval_sec` опрашивает включённые маркетплейсы
       (`marketplaces/*.py`) через их API,
     - суммирует заказы/выручку **за сегодня** (граница дня — локальная,
       смещение из `config["timezone_offset_hours"]`, время синхронизируется
       по NTP при подключении к Wi-Fi),
     - если количество заказов выросло с прошлого опроса — проигрывает на
       зуммере короткую MIDI-мелодию (`buzzer.py` + `notifications/sale.mid`,
       асинхронно, не блокируя веб-сервер и опрос между нотами),
     - обновляет цифры на экране через `display/*`.

## Модуль экрана (два физических размера + симулятор)

Дисплей спрятан за интерфейсом `display/base.py` (`DisplayDriver` —
буфер 1bpp `framebuf`, `width`/`height` задаются в подклассе):

- `display/epd1in54.py` — драйвер SSD1681, 200x200 (сейчас физически
  подключён). Команды сверены с рабочим референс-драйвером
  (Adafruit_CircuitPython_EPD), но не тестировались на реальном железе.
- `display/epd4in2.py` — драйвер под панель WeAct 4.2", 400x300 (пока не
  пришла). Контроллер предположительно SSD1683/UC8176 — уточнить по
  маркировке платы при получении.
- `display/framebuf_sim.py` — программный "дисплей" на базе встроенного
  модуля `framebuf` (тот же формат буфера 1bpp, что и на реальном экране,
  любого размера — `SimDisplay(width=.., height=..)`). Вместо вывода на SPI
  сохраняет кадр как `.bmp` во флеш (`/display_last.bmp`), который можно
  посмотреть через веб-интерфейс (`GET /api/display/preview.bmp`). Позволяет
  разрабатывать и проверять дизайн экрана без железа — `cfg["display"]["screen"]`
  выбирает, макет какого размера симулировать.

Выбор реального драйвера — `cfg["display"]["driver"]`: `"epd1in54"` /
`"epd4in2"` / `"sim"`. Переключение между железом ничего в остальном коде
не меняет.

### Диспетчер макетов

Дизайн экрана — **не** один "резиновый" макет на все размеры, а два разных,
пиксельно точных под каждый экран (400x300 — вдвое больше по площади и
другие пропорции, чем 200x200; тянуть один макет на оба выглядело бы плохо
на каком-то из них):

- `display/layout_common.py` — только общий хелпер отрисовки текста с
  целочисленным масштабом (`draw_scaled_text`, framebuf не умеет
  масштабировать текст сам).
- `display/layout_400x300.py`, `display/layout_200x200.py` — каждый со
  своими координатами: статический макет (что где нарисовано) +
  `update_numbers(fb, data)`, которая обновляет только изменяемые зоны
  (продажи в шт., выручка за день, мелкий IP и время в углу) — разбито так,
  чтобы потом было легко перейти на частичное обновление e-paper.

  `layout_200x200.py` фон (рамки, иконки, разделитель, подписи "ВЫРУЧКА"/
  "ЗАКАЗЫ" кириллицей) рисует не примитивами framebuf, а готовым растром
  `display/assets/bg_200x200.bin` (1bpp MONO_HLSB) — перезагружается через
  `fb.blit()` на **каждой** перерисовке (не только один раз при старте):
  так текст никогда не оставляет "призраков" от старого значения, и не
  нужно держать в коде прямоугольники под затирание, привязанные к
  конкретной картинке.

  Картинку можно менять прямо на плате, без компьютера: кладёшь `.png`
  (200x200) в `display/assets/` (через Thonny/mpremote) — при следующей
  загрузке `check_new_background()` сам конвертирует его в
  `bg_200x200.bin` и удаляет исходник. Конвертирует
  `display/png_to_bin.py` — минимальный PNG-декодер на чистом MicroPython
  (без интерлейса, 8 бит/канал; RGB/RGBA/grayscale/palette; распаковка
  zlib через встроенный модуль `deflate`) — PIL/Pillow на устройстве нет,
  поэтому раньше конвертация делалась только офлайн (см. всё ещё
  существующий `assets/convert_bg_200x200.py` — тот же алгоритм, но на
  компьютере через PIL, годится как запасной путь или для пакетной
  подготовки картинок). `check_new_background()` вызывается один раз при
  старте из `main.py`.

  Поверх фона выручка и заказы рисуются кастомным пиксельным шрифтом
  Orbitron (не встроенным шрифтом framebuf — он не умеет кириллицу и не
  масштабируется): `Fonts/Orbitron/Orbitron.ttf` (в корне проекта, на
  устройство не грузится) растеризован офлайн скриптом
  `assets/generate_orbitron_font.py` в готовые модули с битмапами глифов —
  `display/fonts/orbitron_52.py` (выручка) и `display/fonts/orbitron_42.py`
  (заказы — зона там ниже, упирается в гору-иконку на фоне, поэтому шрифт
  мельче). Свой формат (не micropython-font-to-py): модуль экспортирует
  `HEIGHT`/`SPACING`/`GLYPHS`, рендерит `display/custom_font.py` —
  `draw_text_centered()` и `format_compact()` (если число по ширине не
  влезает — сокращает тысячи в "12.3K", миллионы в "1.2M").

  Где именно рисовать текст (X/Y, какой файл шрифта, порог сокращения в
  K/M) — задаётся текстовым файлом `display/assets/layout.txt`, а не
  константами в коде. Создаётся с дефолтами при первом запуске, если его
  нет; правится вручную (Thonny/mpremote), перечитывается на каждой
  перерисовке — подхватывается сразу, без перезагрузки платы. Опечатка в
  отдельном поле не ломает экран — для этого конкретного поля просто
  вернётся значение по умолчанию (см. `DEFAULTS` в `layout_200x200.py`).

  Время, дата и IP на этом экране пока не выводятся — отложено.
- `display/layout.py` — тонкий диспетчер: `get_layout(width, height)`
  возвращает нужный модуль по размеру активного `DisplayDriver`. Вызывающий
  код (`main.py`, `stats_engine.py`) не завязан на конкретный экран, просто
  спрашивает layout под `display.width`/`display.height`.

## Расширяемость маркетплейсов

`marketplaces/base.py` определяет интерфейс:

```python
class MarketplaceClient:
    id = "base"
    name = "Base"
    def __init__(self, settings): ...
    def fetch_daily_stats(self):
        # -> {"orders": int, "revenue": float}
        raise NotImplementedError
```

`marketplaces/registry.py` хранит `{id: класс}`. Чтобы добавить новый
маркетплейс — создать файл `marketplaces/<id>.py` с классом-наследником и
зарегистрировать в `registry.py`. Веб-интерфейс сам подхватывает список
доступных маркетплейсов из реестра и позволяет включить/выключить и ввести
ключи для каждого.

## Хранение конфигурации

Всё в одном `/config.json` на флеше (см. `config.py`):

```json
{
  "wifi": {"ssid": "...", "password": "..."},
  "ap": {"ssid": "SellerCounter-Setup", "password": "12345678"},
  "poll_interval_sec": 60,
  "timezone_offset_hours": 3,
  "marketplaces": [
    {"id": "ozon", "enabled": true, "client_id": "...", "api_key": "..."},
    {"id": "wb", "enabled": true, "api_key": "..."},
    {"id": "yandex", "enabled": false, "campaign_id": "...", "api_key": "..."}
  ],
  "display": {"driver": "sim", "rotation": 0, "beep_on_sale": true},
  "buzzer": {"pin": 4, "enabled": true}
}
```

API-ключи маркетплейсов не покидают плату — обмен только между браузером
пользователя в локальной сети и самой ESP32.

## Известные ограничения / TODO

- API Ozon/WB/Yandex часто меняются — клиенты в `marketplaces/*.py` написаны
  по документации на момент разработки и **обязательно нужно свериться** с
  актуальными докам продавца перед реальным использованием (эндпоинты,
  структура ответа).
- TLS-запросы к внешним API на ESP32-S3 требуют прошивки MicroPython,
  собранной с mbedTLS (обычно так и есть в стандартных `GENERIC_S3` сборках
  с 16MB flash / 8MB PSRAM — но стоит проверить `ssl` доступен).
  Использование PSRAM для памяти под HTTPS-буферы обязательно (16R8 модуль).
- Веб-сервер использует `microdot` (лёгкий async-фреймворк для MicroPython) и
  клиенты маркетплейсов — `requests`; обе библиотеки вендорены прямо в
  `firmware/lib/` (см. `lib/VENDORED.md`) и заливаются вместе со всем
  остальным кодом — отдельная установка через `mip`/терминал не нужна,
  устройство можно отдавать сразу готовым.
- Реального экрана нет — `epd4in2.py` не протестирован на железе.
